## 🏗️ Архитектурный аудит: что уже работает на будущее

### ✅ Уже заложено правильно:
1. **EventBus как шина данных** — это главное. Стратегии не знают, откуда пришли данные (Binance, Bybit, симулятор). Они просто подписываются на события. Это идеально для смены биржи.
2. **Адаптеры (`adapters/binance_ws.py`, `adapters/binance_rest.py`)** — уже вынесены в отдельный слой. Для Bybit мы просто напишем `adapters/bybit_ws.py` и `adapters/bybit_rest.py`, которые будут публиковать события в том же формате.
3. **`PositionSizer` с fallback** — уже не зависит от биржи на уровне логики (только в методе `get_symbol_info`, который легко заменить).
4. **Конфигурация через JSON** — символы, риски, параметры стратегий уже вынесены.

### ⚠️ Что нужно изменить для мультивалютности:
1. **`BtcContextMonitor` жестко завязан на BTCUSDT** — он подписан только на `BTC_AGG_TRADE`. Для мультивалютки нам нужен мониторинг дельты **по каждому символу**, а не только по BTC.
2. **Стратегии хранят только `self.btc_trend`** — нужно расширить до хранения контекста по своему символу + контекста BTC (как лидера рынка).
3. **`DriftMonitor` и `OrderVerifier`** — уже работают по символу, тут всё ок.

## 🎯 План реализации Уровня 3 (Дивергенции) с учетом будущего

### Шаг 1: Создаем универсальный `DeltaMonitor` (вместо/в дополнение к `BtcContextMonitor`)

Сейчас `BtcContextMonitor` считает дельту за 5-секундное окно и сбрасывает её. Для поиска дивергенций нам нужно **хранить историю** в виде "свечей":

```
[
  {timestamp: ..., price: 78000, delta: +5.2},
  {timestamp: ..., price: 78050, delta: +3.1},  ← цена растет, дельта падает = медвежья дивергенция
  {timestamp: ..., price: 78100, delta: -1.5},
  ...
]
```

**Архитектурное решение:**
- Создаем класс `DeltaMonitor`, который параметризуется символом (`symbol="BTCUSDT"` или `symbol="SOLUSDT"`)
- Он слушает события `TRADE_AGG` (или `AGG_TRADE`) по своему символу
- Копит свечи (например, последние 60 свечей по 1 минуте)
- Анализирует экстремумы цены и дельты на предмет дивергенций
- Публикует событие `DIVERGENCE_DETECTED` с типом (`BULLISH`, `BEARISH`, `NONE`)

**Для мультивалютки:** в `main.py` мы создаем экземпляры `DeltaMonitor` для каждого торгуемого символа + один для BTC как лидера.

**Для Bybit:** адаптер Bybit будет публиковать те же события `TRADE_AGG` в том же формате. `DeltaMonitor` даже не заметит разницы.

### Шаг 2: Расширяем стратегии для работы с дивергенциями

В каждой стратегии (`AbsorptionV2`, `BreakoutV1`, `WallFadeV3`) добавляем:
- Подписку на `DIVERGENCE_DETECTED` по своему символу
- Подписку на `DIVERGENCE_DETECTED` по BTC (для кросс-подтверждения)
- Логику повышения/понижения `confidence` на основе дивергенции

**Пример логики для `AbsorptionV2`:**
- Сигнал LONG на SOL + бычья дивергенция на SOL → `confidence += 0.15`
- Сигнал LONG на SOL + бычья дивергенция на BTC → `confidence += 0.10` (дополнительно)
- Сигнал LONG на SOL + медвежья дивергенция на BTC → `confidence -= 0.20` (предупреждение)

### Шаг 3: Готовим почву для Bybit

Чтобы переход на Bybit был безболезненным, нужно:
1. **Унифицировать формат событий** — создать в `core/events.py` (или аналоге) стандартные типы событий: `TRADE_AGG`, `DEPTH_UPDATE`, `ORDER_UPDATE`. Сейчас они уже почти унифицированы, но нужно это зафиксировать документально.
2. **Абстрагировать `get_exchange_info`** — сейчас `PositionSizer` вызывает метод REST-клиента. Нужно сделать интерфейс `IExchangeInfoProvider`, который реализуют и Binance, и Bybit.

## 📋 Конкретный план действий (по шагам)

Предлагаю двигаться так:

**Этап А: Рефакторинг мониторинга (1-2 сообщения)**
1. Переименовываем/расширяем `BtcContextMonitor` → создаем универсальный `DeltaMonitor`
2. Он работает для любого символа, хранит историю свечей
3. В `main.py` создаем экземпляры: `btc_monitor` (для BTC) + `sol_monitor` (для SOLUSDT)
4. Тестируем, что дивергенции корректно детектируются и публикуются

**Этап Б: Интеграция в стратегии (1 сообщение)**
1. Добавляем в каждую стратегию подписку на `DIVERGENCE_DETECTED`
2. Реализуем логику корректировки `confidence`
3. Тестируем на истории (если есть) или в реальном времени

**Этап В: Подготовка к Bybit (параллельно)**
1. Фиксируем формат событий в документации/комментариях
2. Создаем абстракцию для `get_exchange_info`
3. Это не блокирует текущую работу, но закладывает фундамент

4. **По Bybit:** есть примерный срок перехода? Если через месяц — делаем полную абстракцию сейчас. Если через полгода — можно отложить часть рефакторинга.
