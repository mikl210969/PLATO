# 📄 PLATO v3.0 — Текущее состояние архитектуры (Актуально на 2026-08-30)

**Статус:** Спринт 5 (Фундамент Order Flow) завершен. Система готова к стресс-тестам и внедрению динамического риск-менеджмента.

## 🏛️ 1. Архитектурные принципы
- **Spot = Источник истины:** Анализ стакана, дельты и поглощения ведется по спотовым данным (низкие комиссии, чистая ликвидность).
- **Futures = Инструмент исполнения:** Все ордера отправляются на фьючерсный рынок в Hedge Mode.
- **Событийная модель (Event-Driven):** Все модули общаются через `EventBus`. Нет жестких вызовов методов между независимыми компонентами.
- **Защита от сбоев (Force Sync):** Если WebSocket теряет событие исполнения, `DriftMonitor` автоматически синхронизирует состояние с биржей и активирует защиту.

## ✅ 2. Реализованные модули (Готово к использованию)

### 2.1. Слой данных (Market Data Layer)
- [x] **Binance WS Adapter:** Подключены спотовый стакан (`depth@100ms`), спотовые сделки (`aggTrade`), фьючерсный стакан и User Data Stream.
- [x] **Binance REST Client:** Получение свечей (klines), проверка позиций, статус ордеров, отмена ордеров.
- [x] **SpotPriceProvider:** Агрегатор спотовой mid-price для точного определения цены входа.

### 2.2. Аналитическое ядро (Analytics Hub)
- [x] **DeltaAnalyzer:** Скользящее окно (30-60 мин), расчет кумулятивной дельты и скорости дельты (velocity).
- [x] **VolatilityFilter:** Расчет **реального ATR** из свечей (больше никаких заглушек `0.5`).
- [x] **ImbalanceCalculator:** Расчет дисбаланса ликвидности по топ-10 уровням стакана.
- [x] **HVNCalculator:** Двухуровневая система: **Micro-HVN** (60 мин, для точного входа и SL) и **Macro-HVN** (24 ч, как глобальный фильтр).
- [x] **TrendContext:** Определение состояния рынка (UPTREND, DOWNTREND, RANGING) для фильтрации Continuation/Reversal сделок.
- [x] **AbsorptionDetector:** Детектирует паттерн "цена не двигается при высокой агрессивной дельте" (поглощение ликвидности).
- [x] **BreakoutDetector:** Отслеживает скорость "поедания" стены (порог 60%, скорость 5%/сек, защита от подлива 50%).

### 2.3. Стратегии (Strategies)
- [x] **WallFadeV3:** Отскок от Micro-HVN. SL привязан к уровню HVN. Использует `TrendContext` для фильтрации.
- [x] **AbsorptionV2:** Событийная стратегия. Входит в сделку сразу после события `ABSORPTION_DETECTED` с расчетом SL/TP на основе ATR.
- [x] **BreakoutV1:** Событийная стратегия пробоя. Оценивает "пустоту ликвидности" за стеной. Генерирует параметры для **гибридного исполнения** (limit с таймаутом 5 сек → fallback на market).

### 2.4. Исполнение и Риск-менеджмент (Execution & Risk)
- [x] **Trader:** Отправка ордеров в Hedge Mode. **Критическое исправление:** жесткая валидация `client_order_id` (защита от пустых строк/пробелов, fallback на `ORD_{passport_id}`).
- [x] **RiskManager (Internal Stop):** Следит за ценой через WS. При достижении TP1 закрывает 50% и переносит SL в безубыток. При TP2/SL закрывает остаток рыночным ордером.
- [x] **OrderVerifier:** REST-фоллбэк. Опрос биржи каждые 3 сек (до 20 попыток) для подтверждения статуса ордера, если WS молчит.
- [x] **LifecycleManager:** TTL-таймеры для лимитных ордеров. Автоматическая отмена неисполненных ордеров.
- [x] **DriftMonitor:** **Критическое исправление (Force Sync):** Если паспорт в статусе `ORDER_SENT`, а на бирже уже есть позиция (`size > 0`), монитор автоматически меняет статус на `OPEN` и публикует `POSITION_OPENED`, заставляя `RiskManager` выставить защиту.

## 🛠️ 3. Критические исправления последних 2 дней (Важно для контекста!)

1. **Проблема "Потерянного ордера":** Ранее `client_order_id` мог быть пустым или содержать пробел (`" "`), из-за чего `OrderHandler` не мог найти паспорт при получении события от биржи.
   - **Решение:** Внедрен метод `_generate_rich_client_order_id`. Формат: `{SYMBOL_4}_{STRATEGY_10}_{PASSPORT_SHORT}_{TIMESTAMP}` (макс. 35 символов). Пример: `SOLU_Absorption_1ff4a4_1788044341`.
2. **Проблема "Позиции без защиты":** При обрыве WS событие `FILLED` терялось. Паспорт застревал в `ORDER_SENT`, позиция на бирже была открыта, но SL/TP не выставлялись.
   - **Решение:** Добавлена логика **Force Sync** в `DriftMonitor._check_drift`. Теперь расхождение `ORDER_SENT` + `exchange_size > 0` автоматически лечится.
3. **Проблема Pylance `reportOptionalMemberAccess`:** Методы `Trader` могли вернуть `None`, что вызывало ошибки типов при вызове `.get()`.
   - **Решение:** Внедрен паттерн Early Return с проверкой `if result and isinstance(result, dict):` перед любым доступом к словарю.
