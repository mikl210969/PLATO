### Описание параметров:

### 🚨 КРИТИЧЕСКАЯ ПРОБЛЕМА: Утечка секретов

**API-ключи лежат в `exchange.json` в открытом виде!**

В `main.py` есть fallback:
```python
api_key = secrets.get('api_key', '') or exchange_config.get('api_key', '')
```

Это означает, что если ключи есть в `exchange.json`, они будут прочитаны оттуда, даже если `secrets.json` пуст или отсутствует.

**Риски:**
- Если этот файл попадёт в Git-репозиторий, ключи будут скомпрометированы.
- Судя по структуре проекта, `exchange.json` **не в `.gitignore`**.

**Решение:**
1. Немедленно удалить `api_key` и `api_secret` из `exchange.json`.
2. Добавить `exchange.json` в `.gitignore` (или убедиться, что там нет чувствительных данных).
3. Все секреты хранить строго в `secrets.json`.
4. Убрать fallback в `main.py` — если ключей нет в `secrets.json`, падать с понятной ошибкой.

### ⚠️ Дополнительная проблема: `testnet` не используется

Параметр `testnet: true` загружается, но нигде в коде не проверяется. Платформа не переключает поведение в зависимости от этого флага.

**Рекомендация:** использовать этот флаг для выбора URL-адресов или для отключения стоп-ордеров на Testnet (где они не работают через стандартный API).

## 📊 2. `config/trading.json` — Параметры торговли

### Текущее содержимое:
```json
{
  "lot_size": 7.0,
  "entry_order_type": "market",
  "ttl_seconds": 300,
  "ttl_action": "convert_to_market",
  "atr_value": 0.5,
  "atr_multiplier_sl": 20.0,
  "atr_multiplier_tp1": 2.0,
  "atr_multiplier_tp2": 3.0
}
```

### Описание параметров:

| Параметр | Тип | Назначение | Кто использует |
| :--- | :--- | :--- | :--- |
| `lot_size` | `float` | Размер позиции (в единицах инструмента) | `Orchestrator._on_signal()`, `Orchestrator._on_ttl_expired()` |
| `entry_order_type` | `str` | Тип входного ордера (`market` / `limit`) | `Orchestrator._on_signal()` |
| `ttl_seconds` | `int` | Время жизни лимитного ордера (секунды) | `LifecycleManager` |
| `ttl_action` | `str` | Действие при истечении TTL (`convert_to_market` / `cancel`) | `Orchestrator._on_ttl_expired()` |
| `atr_value` | `float` | **Статическое значение ATR** | `Orchestrator._on_signal()` → `ExitCalculator` |
| `atr_multiplier_sl` | `float` | Множитель ATR для Stop-Loss | `ExitCalculator` |
| `atr_multiplier_tp1` | `float` | Множитель ATR для Take-Profit 1 | `ExitCalculator` |
| `atr_multiplier_tp2` | `float` | Множитель ATR для Take-Profit 2 | `ExitCalculator` |

### 🚨 КРИТИЧЕСКАЯ ПРОБЛЕМА: Инвертированный Risk/Reward

Давай посчитаем реальные уровни для SOLUSDT (предположим, цена входа $150):

- **ATR** = 0.5 (статический, не зависит от волатильности).
- **Stop-Loss** = `entry_price - (ATR × 20.0)` = $150 - (0.5 × 20) = **$140** (расстояние $10).
- **Take-Profit 1** = `entry_price + (ATR × 2.0)` = $150 + (0.5 × 2) = **$151** (расстояние $1).
- **Take-Profit 2** = `entry_price + (ATR × 3.0)` = $150 + (0.5 × 3) = **$151.5** (расстояние $1.5).

**Соотношение Риск/Прибыль (R:R):**
- Риск: $10 на сделку.
- Прибыль (TP1, 50% объёма): $1.
- Прибыль (TP2, 50% объёма): $1.5.
- **Средняя прибыль** = 0.5 × $1 + 0.5 × $1.5 = **$1.25**.

**Итог:** Платформа рискует **$10**, чтобы заработать **$1.25**. Соотношение R:R = **1 : 0.125**.

Это математически убыточная модель! Чтобы быть в безубытке, винрейт (процент побед) должен быть **~89%**.

**Вероятная причина:** Ошибка в конфиге. Скорее всего, множители перепутаны местами.

**Рекомендации:**
- **Вариант 1:** Поменять местами: `atr_multiplier_sl: 2.0`, `atr_multiplier_tp1: 10.0`, `atr_multiplier_tp2: 15.0`.
- **Вариант 2:** Сделать `atr_value` динамическим (рассчитывать на основе свечей) и уменьшить его (например, до 0.05).
- **Вариант 3:** Добавить валидацию в `ExitCalculator`, которая проверяет, что `tp1_mult > sl_mult` и `tp2_mult > tp1_mult`.

### ⚠️ Дополнительная проблема: Статический ATR

`atr_value = 0.5` — это **статическое значение**, которое не зависит от реальной волатильности рынка. В период высокой волатильности уровни будут слишком близко, в период низкой — слишком далеко.

**Рекомендация:** рассчитывать ATR динамически на основе последних N свечей (например, через `ta-lib` или `pandas`).

## 🛡️ 3. `config/risk.json` — Глобальный риск-менеджмент

### Текущее содержимое:
```json
{
    "max_position_size": 7.0,
    "max_daily_loss": 10.0,
    "max_drawdown": 0.05,
    "max_trades_per_hour": 5,
    "cooldown_seconds": 5
}
```

### Описание параметров:

| Параметр | Тип | Назначение | Кто использует |
| :--- | :--- | :--- | :--- |
| `max_position_size` | `float` | Максимальный размер позиции | ⚠️ **НИКТО** |
| `max_daily_loss` | `float` | Максимальный дневной убыток (USDT) | ⚠️ **НИКТО** |
| `max_drawdown` | `float` | Максимальная просадка (доля, 0.05 = 5%) | ⚠️ **НИКТО** |
| `max_trades_per_hour` | `int` | Максимум сделок в час | ⚠️ **НИКТО** |
| `cooldown_seconds` | `int` | Задержка между сигналами | ⚠️ **НИКТО** (в Orchestrator захардкожено 10 сек) |

### 🚨 КРИТИЧЕСКАЯ ПРОБЛЕМА: Мёртвый Risk-менеджмент

**Ни один из этих параметров нигде не проверяется в коде!**

Я просмотрел весь код `RiskManager`, `Orchestrator` и `Trader`. `RiskManager` в текущей реализации — это просто "выставлятор" TP/SL ордеров. Он **не защищает депозит** от:
- Превышения дневного лимита убытков ($10).
- Превышения максимальной просадки (5%).
- Слишком частой торговли (5 сделок в час).
- Превышения максимального размера позиции.

**Риск:** Если стратегия войдёт в серию убыточных сделок (а при R:R 1:0.125 это неизбежно), платформа будет торговать до полного слива депозита, игнорируя `risk.json`.

**Рекомендация:** Добавить в `Orchestrator` или создать отдельный `GlobalRiskManager`, который будет проверять эти лимиты перед каждым `_on_signal()`:

```python
# Псевдокод для GlobalRiskManager
async def can_open_position(self) -> bool:
    if self.daily_pnl <= -self.config['max_daily_loss']:
        return False
    if self.drawdown >= self.config['max_drawdown']:
        return False
    if self.trades_last_hour >= self.config['max_trades_per_hour']:
        return False
    return True
```

### ⚠️ Дополнительная проблема: `cooldown_seconds` не используется

В конфиге `cooldown_seconds: 5`, но в `Orchestrator.__init__()`:
```python
self._signal_cooldown = 10  # секунд (захардкожено)
```

**Рекомендация:** читать из конфига: `self._signal_cooldown = config.get('risk', {}).get('cooldown_seconds', 10)`.

{

### Описание параметров по стратегиям:

#### WallFade (Включена ✅)

| :--- | :--- | :--- | :--- |
| `enabled` | `true` | Флаг активности | ✅ Да |
| `min_wall_volume` | `20.0` | Минимальный объём стенки | ✅ Да |
| `min_confidence` | `0.3` | Минимальная уверенность | ❌ **Мёртвый параметр** |
| `price_distance_pct` | `0.5` | Максимальное расстояние до стенки (%) | ✅ Да |

#### Absorption (Отключена ❌)

| `min_confidence` | `0.3` | Минимальная уверенность | ❌ **Мёртвый параметр** |

#### Breakout (Включена, но не работает ⚠️)
| Параметр | Значение | Назначение | Используется? |
| :--- | :--- | :--- | :--- |
| `enabled` | `true` | Флаг активности | ✅ Да |
| `min_volume` | `10.0` | Минимальный объём | ❌ **Мёртвый параметр** |
| `min_confidence` | `0.3` | Минимальная уверенность | ❌ **Мёртвый параметр** |
| `lookback_bars` | `20` | Количество свечей для анализа | ✅ Да |
| `breakout_threshold` | `0.5` | Порог пробоя (%) | ❌ **Мёртвый параметр** |

### 🚨 КРИТИЧЕСКАЯ ПРОБЛЕМА: Фактически работает только ОДНА стратегия

1. **WallFade**: `enabled: true`. Работает. Ищет стенки в стакане и шортит от них.
2. **Absorption**: `enabled: false`. **Отключена в конфиге.** Не генерирует сигналы.
3. **Breakout**: `enabled: true`. НО, как мы выяснили при разборе `main.py`, в контекст **не передаются свечи** (`candles`). Стратегия проверяет `if not candles: return None` и **никогда не сгенерирует сигнал**.

**Итог:** Из трёх заявленных стратегий в продакшене (на тестнете) фактически торгует **только WallFade**. Причём торгует она с инвертированным R:R (огромный стоп, микроскопические тейки).

### ⚠️ Дополнительные проблемы:

#### 1. Мёртвые параметры во всех стратегиях
Во всех трёх стратегиях есть параметры, которые читаются из конфига, но **нигде не используются**:
- `min_confidence` — должен фильтровать сигналы по уверенности, но `confidence` захардкожен.
- `min_wall_volume` в Absorption — не используется в логике.
- `min_volume` и `breakout_threshold` в Breakout — не используются.

#### 2. Нет валидации конфига
`ConfigLoader` не проверяет, что конфиг содержит необходимые параметры. Если в `strategies.json` отсутствует ключевой параметр, стратегия может работать некорректно.

**Рекомендация:** добавить валидацию схемы конфига (например, через `pydantic` или `jsonschema`).

#### 3. Нет параметров для динамического расчёта
Все пороги захардкошены в коде или в конфиге как статические значения. Нет возможности адаптировать их к рыночным условиям.

## 🔐 5. `config/secrets.json` — API-ключи

### Ожидаемая структура:
```json
{
    "api_key": "your_api_key_here",
    "api_secret": "your_api_secret_here"
}
```

### Описание параметров:

| Параметр | Тип | Назначение |
| :--- | :--- | :--- |
| `api_key` | `str` | API-ключ Binance |
| `api_secret` | `str` | API-секрет Binance |

### Требования безопасности:
1. **Файл должен быть в `.gitignore`** — никогда не коммитить ключи в Git.
2. **Права доступа:** файл должен быть доступен только владельцу (`chmod 600 secrets.json`).
3. **Не логировать ключи** — убедиться, что `api_key` и `api_secret` никогда не попадают в логи.
4. **Использовать тестовые ключи** для разработки, боевые — только в продакшене.

### ⚠️ Проверка `.gitignore`

Убедись, что в `.gitignore` есть строки:
```
config/secrets.json
config/exchange.json  # если там есть ключи
```
