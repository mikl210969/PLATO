## 🏛️ Общее описание платформы: PLAT_WALLS_NEW

**Назначение:**  
Торговая система для автоматической торговли криптовалютными фьючерсами (Binance). Платформа анализирует рыночные данные (стакан, цена), генерирует сигналы на основе стратегий, управляет позициями и защитными ордерами (SL/TP).

**Ключевые особенности:**  
- Событийно-ориентированная архитектура (EventBus).  
- WebSocket как основной канал данных, REST — для отправки команд и резерва.  
- Единый источник правды — **Паспорт сделки** (Passport).  
- Модульность: каждый компонент отвечает за свою зону ответственности.  
- Возможность восстановления после сбоев (RecoveryManager).

## 🔄 Жизненный цикл сделки

1. **Сигнал** → стратегия публикует `SIGNAL_GENERATED` в шину.
2. **Оркестратор** получает сигнал, проверяет `is_symbol_busy()`, создаёт **паспорт**.
3. **Trader** отправляет MARKET-ордер на биржу через REST.
4. **Оркестратор** обрабатывает `ORDER_TRADE_UPDATE` и обновляет паспорт → `OPEN`.
5. **RiskManager** выставляет TP1, TP2, SL (лимитные ордера).
6. **Оркестратор** обрабатывает обновления ордеров и счета:
   - TP1 → частичное закрытие, перенос SL в безубыток.
   - TP2 → полное закрытие.
   - SL → полное закрытие.
   - Ручное закрытие → отмена всех лимитных ордеров.
7. **Паспорт** сохраняется на диск и закрывается.

## ⚙️ Основные компоненты и их ответственность

| Компонент | Ответственность |
| :--- | :--- |
| **Orchestrator** | Управляет процессом: сигналы → паспорт → команды трейдеру |
| **Trader** | Исполняет ордера, возвращает результат |
| **RiskManager** | Выставляет и отменяет защитные ордера (TP/SL) |
| **StateManager** | Контролирует разрешённые переходы статусов паспорта |
| **Passport** | Единый источник правды по сделке |
| **PassportManager** | Кэш паспортов в памяти |
| **PassportRepository** | Сохранение/загрузка паспортов на диск |
| **LifecycleManager** | Управляет временем жизни лимитных ордеров (TTL) |
| **RecoveryManager** | Восстанавливает состояние платформы после перезапуска |
| **BinanceRestClient** | Отправка команд на биржу (REST) |
| **BinanceWsAdapter** | Получение данных с биржи (WebSocket) |
| **ChannelRouter** | Выбор канала (WS/REST) для запросов |

---

## 🔐 Ключевые принципы

1. **Биржа — источник правды.** Паспорт синхронизируется с реальным состоянием.
2. **Паспорт — единый источник правды для платформы.** Все модули читают/пишут только через него.
3. **События — основной способ общения.** Модули слабо связаны, общаются через `EventBus`.
4. **REST — для команд, WS — для данных.** REST не используется для получения данных в цикле.

## 📄 Описание файла: `trading/orchestrator.py`

**Назначение:**  
Главный управляющий модуль платформы. Он **принимает все решения** о том, что делать с сигналами, ордерами и паспортами.

**Роль в архитектуре:**  
«Мозг» платформы. Оркестратор **не** отправляет ордера на биржу напрямую (это делает `Trader`) и **не** выставляет защиту (это делает `RiskManager`). Он **управляет процессом**:

- Слушает события из `EventBus`.
- Создаёт и обновляет паспорта (`PassportManager`).
- Проверяет, можно ли открыть позицию (`is_symbol_busy`).
- Отправляет команды `Trader` на открытие/закрытие.
- Публикует события (`POSITION_OPENED`, `TP1_FILLED` и т.д.) для других модулей.
- Обрабатывает обновления от биржи (`ORDER_TRADE_UPDATE`, `ACCOUNT_UPDATE`).

---

### 🔗 Ключевые зависимости (кто вызывает)

| Кто вызывает | Что делает |
| :--- | :--- |
| `main.py` | Создаёт экземпляр, передаёт `EventBus`, `PassportManager`, `RiskManager` и запускает `start()`. |
| `EventBus` | Доставляет события в обработчики Оркестратора (`_on_signal`, `_on_order_update` и т.д.). |

---

### 🧠 Основные методы (без кода, просто описание)

- **`_on_signal()`**  
  Получает сигнал от стратегии. Проверяет, занят ли символ, создаёт паспорт, рассчитывает уровни (через `Trader`), отправляет команду трейдеру.

- **`_on_order_update()`**  
  Обрабатывает обновления ордеров (`ORDER_TRADE_UPDATE`). Обновляет размер позиции, обрабатывает срабатывание TP1/TP2/SL.

- **`_on_account_update()`**  
  Обрабатывает обновления счёта (`ACCOUNT_UPDATE`). Синхронизирует паспорт с реальным размером позиции на бирже. При `position_size = 0` вызывает отмену ордеров через `RiskManager`.

- **`_on_position_closed()`**  
  Закрывает паспорт, когда позиция закрыта (по TP/SL/вручную).

- **`_on_sync_request()`**  
  Обрабатывает запрос на синхронизацию (например, после переподключения WS). Делает REST-запрос к бирже и сверяет паспорт.

- **`set_risk_manager()`**  
  Передаёт ссылку на RiskManager (вызывается из `main.py`).

---

### 📦 Какие данные хранит

- `traders` — словарь зарегистрированных трейдеров (по символу).
- `_last_signal_time` — время последнего сигнала (для защиты от спама).
- `_running` — флаг работы (True/False).
- `risk_manager` — ссылка на объект RiskManager.

## 📄 Описание файла: `trading/trader.py`

**Назначение:**  
Исполнительный модуль платформы, который **отвечает исключительно за отправку ордеров на биржу** и возврат результата. Он не принимает решений, не анализирует данные, не работает с паспортами.

**Роль в архитектуре:**  
«Руки» платформы. Получает команду от Оркестратора, формирует запрос к `BinanceRestClient` и возвращает результат. Не знает про стратегии, паспорта или риск-менеджмент.

---

### 🔗 Ключевые зависимости (кто вызывает)

| Кто вызывает | Что делает |
| :--- | :--- |
| `Orchestrator` | Вызывает `execute_order()` для открытия позиции и `close_position()` для закрытия. |
| `RiskManager` | Вызывает `execute_order()` для установки TP/SL (через Оркестратора). |

---

### 🧠 Основные методы

- **`execute_order()`**  
  Принимает параметры ордера (`symbol`, `side`, `quantity`, `order_type`).  
  Поддерживает `market`, `limit`, `stop_market`, `stop_limit`.  
  Возвращает унифицированный словарь с результатом: `success`, `order_id`, `status`, `error`.

- **`close_position()`**  
  Определяет сторону позиции (long/short), отправляет рыночный ордер на закрытие с `reduce_only=True`.

- **`cancel_order()`**  
  Отменяет ордер по `order_id` через REST.

- **`calculate_exit_levels()`**  
  Рассчитывает уровни SL/TP через `ExitCalculator`. Используется Оркестратором при создании паспорта.

- **`get_position_from_exchange()`**  
  Запрашивает текущую позицию через REST (используется для синхронизации).

---

### 📦 Какие данные хранит

- `symbol` — торговый инструмент.
- `config` — конфигурация (размер лота, типы ордеров).
- `exit_calculator` — экземпляр калькулятора уровней.

## 📄 Описание файла: `adapters/binance_rest.py`

**Назначение:**  
HTTP-клиент для взаимодействия с Binance через REST API. Отвечает за все «тяжёлые» запросы, которые требуют подписи и/или не могут быть выполнены через WebSocket.

**Роль в архитектуре:**  
«Мост» между платформой и биржей для **отправки команд** (создание/отмена ордеров). В отличие от WebSocket (который слушает события), REST используется для **активных действий**.

---

### 🔗 Ключевые зависимости (кто вызывает)

| Кто вызывает | Что делает |
| :--- | :--- |
| `Trader` | Вызывает методы для отправки MARKET, LIMIT, STOP ордеров. |
| `Platform` (main.py) | Вызывает `get_listen_key()` для получения ключа WebSocket. |
| `RecoveryManager` | Вызывает `get_position()` для синхронизации. |

---

### 🧠 Основные методы

- **`create_market_order()`**  
  Отправляет рыночный ордер. Формирует подпись, отправляет POST-запрос, возвращает результат.

- **`create_limit_order()`**  
  Отправляет лимитный ордер. Принимает цену и количество.

- **`cancel_order()`**  
  Отменяет ордер по `order_id`. Использует DELETE-запрос.

- **`get_position()`**  
  Запрашивает текущую позицию по символу (через `/fapi/v2/positionRisk`).

- **`get_listen_key()` / `renew_listen_key()`**  
  Управляют ключом для WebSocket-канала (user data stream).

---

### 📦 Какие данные хранит

- `api_key`, `api_secret` — для подписи запросов.
- `base_url` — эндпоинт биржи (тестовая или реальная сеть).
- `_session` — клиентская сессия `aiohttp` для переиспользования соединений.

## 📄 Описание файла: `adapters/binance_ws.py`

**Назначение:**  
WebSocket-клиент для Binance. Отвечает за **приём данных в реальном времени** (стакан, обновления ордеров, состояние счета). В отличие от REST, это пассивный канал — он только слушает и передает события в платформу.

**Роль в архитектуре:**  
«Уши» платформы. Основной канал получения данных с биржи. WebSocket — это **приоритетный** источник информации, REST используется только для отправки команд и редкой синхронизации.

---

### 🔗 Ключевые зависимости (кто вызывает)

| Кто вызывает | Что делает |
| :--- | :--- |
| `Platform` (main.py) | Создает экземпляр, подписывается на каналы (`subscribe_depth`, `subscribe_user_data`), запускает цикл обработки (`run`). |
| `EventBus` | Обработчики событий (`on_order_update`, `on_account_update`) публикуют полученные данные в шину. |

---

### 🧠 Основные методы

- **`connect()`**  
  Устанавливает WebSocket-соединение с повторными попытками (до 3 раз). После успешного подключения вызывает колбэк `_on_reconnect`.

- **`subscribe_depth()`**  
  Подписывается на обновления стакана (20 уровней, 100 мс) для указанного символа.

- **`subscribe_user_data()`**  
  Подписывается на персональный канал (`listen_key`) для получения обновлений ордеров и состояния счета.

- **`run()`**  
  Основной цикл обработки входящих сообщений. Получает данные, парсит JSON и передает в `_handle_message()`.

- **`_handle_message()`**  
  Маршрутизатор входящих событий. Распознает типы событий (`ORDER_TRADE_UPDATE`, `ACCOUNT_UPDATE`, `depthUpdate`), формирует унифицированные payload'ы и вызывает зарегистрированные обработчики.

- **`on()`**  
  Регистрирует обработчик для конкретного типа события.

---

### 📦 Какие данные хранит

- `_ws` — активное WebSocket-соединение.
- `_handlers` — словарь с обработчиками событий (ключ — тип события, значение — функция-обработчик).
- `_json_logger` — логгер для записи всех входящих сообщений в JSON-файл.
- `_on_reconnect` — колбэк, вызываемый после переподключения.

## 📄 Описание файла: `adapters/channel_router.py`

**Назначение:**  
Маршрутизатор, который выбирает канал связи (WebSocket или REST) для отправки команд и получения данных. Это прослойка, которая позволяет платформе автоматически переключаться между WS и REST в зависимости от состояния соединения.

**Роль в архитектуре:**  
«Диспетчер каналов» — определяет, через какой канал отправлять запрос:  
- Если WebSocket здоров, использует его (быстрее, меньше нагрузки на REST лимиты).  
- Если WS упал или недоступен, переключается на REST (резервный канал).

---

### 🔗 Ключевые зависимости (кто вызывает)

| Кто вызывает | Что делает |
| :--- | :--- |
| `Trader` (через `Platform`) | Может вызывать `send_order()` для отправки ордера. |
| `Platform` (main.py) | Может вызывать для синхронизации состояния. |

---

### 🧠 Основные методы

- **`send_order()`**  
  Отправляет ордер. Если WS здоров — использует `ws.send_order()`, иначе — `rest.create_market_order()`.

- **`cancel_order()`**  
  Отменяет ордер через WS или REST (аналогично).

- **`get_position()`**  
  Получает позицию через WS или REST.

- **`set_ws_healthy()`**  
  Вручную устанавливает статус WS (используется при обнаружении ошибок).

---

### 📦 Какие данные хранит

- `ws` — ссылка на экземпляр `BinanceWsAdapter`.
- `rest` — ссылка на экземпляр `BinanceRestClient`.
- `ws_healthy` — флаг состояния WS (True/False).

---

### ⚠️ Примечание

В текущей реализации большинство методов WS (`send_order`, `cancel_order`, `get_position`) пока **не реализованы** (возвращают ошибку). Router используется как заготовка для будущего переключения, а пока работает в режиме REST-fallback.

## 📄 Описание файла: `main.py`

**Назначение:**  
Главный входной файл платформы. Отвечает за инициализацию всех компонентов, запуск основного цикла и управление жизненным циклом приложения.

**Роль в архитектуре:**  
«Дирижер оркестра» — создает все необходимые объекты, связывает их между собой, запускает основные процессы и обрабатывает сигналы остановки (Ctrl+C).

---

### 🔗 Ключевые зависимости (кто вызывает)

| Кто вызывает | Что делает |
| :--- | :--- |
| **Пользователь** | Запускает `python main.py` |
| **Система** | Вызывает `signal_handler()` при получении сигнала завершения |

---

### 🧠 Основные компоненты, инициализируемые в `Platform.__init__()`

| Компонент | Назначение |
| :--- | :--- |
| `EventBus` | Центральная шина событий |
| `PassportManager` | Хранилище паспортов в памяти |
| `PassportRepository` | Сохранение/загрузка паспортов на диск |
| `BinanceRestClient` | HTTP-клиент для биржи |
| `BinanceWsAdapter` | WebSocket-клиент для биржи |
| `ChannelRouter` | Маршрутизатор между WS и REST |
| `StateManager` | Управление переходами состояний |
| `Orchestrator` | Главный управляющий модуль |
| `Trader` | Исполнитель ордеров |
| `RiskManager` | Управление защитными ордерами |
| `LifecycleManager` | Управление TTL ордеров |
| `RecoveryManager` | Восстановление после перезапуска |
| `WallFadeStrategy` и др. | Торговые стратегии |

---

### 🔄 Основные методы

- **`_main_loop()`**  
  Основной цикл платформы:  
  1. Получает `listen_key` через REST.  
  2. Подключается к WebSocket.  
  3. Подписывается на стакан и пользовательские данные.  
  4. В цикле: получает цену и стакан из WS, генерирует сигналы стратегий, публикует их в шину.

- **`_keep_alive_loop()`**  
  Продлевает `listen_key` каждые 20 минут (чтобы WebSocket-сессия не истекла).

- **`run()`**  
  Запускает Оркестратор и основной цикл.

- **`stop()`**  
  Останавливает все компоненты и закрывает соединения.

---

### 📦 Какие данные хранит

- `ws_price` — последняя цена из WebSocket.
- `ws_orderbook` — последний стакан из WebSocket.
- `_listen_key` — ключ для пользовательского WebSocket-канала.
- `_running` — флаг работы платформы.

---

### ⚠️ Особенности

- **WS приоритетнее REST**: цена и стакан берутся из WS, REST используется только как fallback.
- **Восстановление отключено**: `RecoveryManager.recover()` закомментирован.
